## Immutable snapshots

`src/recycleguard/snapshots.py` uses the shared V02 connection/coordinator.
`SnapshotPublication` pins exact membership/coverage blobs, source receipts and the
expected scope head. Missing and failed receipts remain accounted for. Creation
metadata comes from the service, never the publication JSON.

The head compare-and-swap, immutable insert, operation result and audit event share
one BEGIN IMMEDIATE transaction. A stale head cannot overwrite a newer snapshot.
Pinned snapshot lookup verifies membership digest, membership/coverage bytes and receipt
references without substituting the latest head. Review binds target ID, membership
digest and expected head, then creates an
APPROVED or REJECTED child. Original snapshot bytes remain unchanged.

`CaseReopen` requires CASE membership, an exact parent and a nonempty reason.
The caller supplies a complete revised manifest, rather than an implicit mutable
patch. Its reason and manifest references are archived in the operation request.
Publication preserves bytes and provenance; it does not turn uncertain observations
into valid evidence or claim complete extraction. H03/S02/A04 supply the real
normalized membership and coverage content.

## Immutable calculation profiles

`src/recycleguard/contracts/profiles.py` defines the supported executable policy
subset. `src/recycleguard/profiles.py` stores immutable `(profile_id, profile_version)`
revisions and a separately advanced head, using the same audited transaction.
Parent versions are retained in the registry. Digests cover canonical UTF-8 JSON
of every CalculationProfile field except `digest` itself, including review state
and review references.

- Draft publication checks the expected ProfileRef, policy shape and exact source
  revision/hash dependencies. Every policy evidence reference must pin one of those
  source revisions. Referenced source bytes are read and hash-verified.
- Review binds profile ID, version and digest. Only a current draft can be reviewed;
  a new version receives the decision and audited human operation reference.
- Approved-only lookup uses the exact ProfileRef, not a mutable “latest” profile.
  It verifies the stored digest and source bytes again before downstream use.
  A subsequent draft does not rewrite or invalidate a previously pinned approval.
- The subset uses supplied metal-wise obligations, supported allocations and
  separate historical liabilities. Supplied Au/Cu/Al/Fe buckets are allowed;
  gold adjustments, sales-derived targets, refurbishing, tax/pricing, solar and
  environmental-compensation calculations remain unsupported.
- Profiles declare all nine eligibility conditions as TESTABLE or UNAVAILABLE.
  Missing facts remain UNRESOLVED. Event equivalence requires the complete exact
  key and corroboration; conflicts/coarse collisions remain PENDING. Liability
  priority is evaluated at allocation time; missing history is unresolved.
- Numeric policy fixes precision 28, four display places, ROUND_HALF_EVEN and
  inexact/overflow traps. Only final display rounding is permitted. These are
  declarations for the later calculation tools, not arithmetic results from A03.
- Purchase-ceiling policy stays DISABLED_REVIEW_REQUIRED in the supported seed.
  An APPROVED slot requires a successful dedicated `review.purchase_ceiling`
  operation bound to the exact policy bytes, excluding state/review_ref. A successful
  unrelated review cannot authorize it. No dedicated ceiling review command or
  automatic legal interpretation is supplied here; H04 must establish that authority.

The store verifies source existence and byte identity, not the legal meaning of a
clause or whether a proposed applicability assertion is substantively correct.
H04 supplies actual reviewed content; the human reviewer must inspect it.

## C05 service and trusted CLI

`CaseService` exposes `publish_case`, `publish_corpus`, `reopen_case`,
`review_snapshot`, `publish_profile` and `review_profile`. The latter covers
approve/reject decisions. Calls receive CommandContext plus an opaque capability
and return ServiceResult with typed output, archived output blob, issues and audit
IDs. Profile results expose source dependencies. Invalid/stale/missing-input
outcomes are explicit; bound operational rejections are archived and replay with
the original issue and audit references. Authentication/schema preflight failures
may occur before an audit intent exists and do not claim a recorded event.

Exact successful replay returns the archived revision without new writes. An
operation ID bound to other input cannot disclose that operation's output. Audit
or storage I/O failures return OUTCOME_UNKNOWN, with no automatic retry or claim
that publication succeeded. The caller must inspect durable state before recovery.

`local_application` composes only fixed service grants, or human review grants
after successful password authentication. JSON cannot supply an actor, session,
method name or capability. Handles are revoked on application exit.

`reviewer init` explicitly enrolls the local data-root owner once, using a password
of at least 12 characters, a random salt and scrypt. Credentials are created
exclusively with owner-only permissions. Review reauthenticates, rejects symlinked,
foreign-owned or group/world-accessible credentials, and creates a fresh session
reference. Passwords are not archived or echoed. Each CLI invocation creates a new
operation context; resubmitting a review is a new operation and a stale-head check,
not cross-invocation idempotent replay. Programmatic callers retain contexts for
exact replay.

This local CLI currently supports **macOS/Linux** credential ownership checks.
It trusts the OS user and configured data root; it is not isolation from Python
code or another process running as that user. Bootstrap is not external identity
verification, statutory signatory authorization, portal access or a C13 report
approval. A browser login, multi-user account management and recovery UI are outside
this handoff. No new dependency or OCR/model selection was introduced.
