## Repaired boundary

- Catalog writes require an active shared AuditKernel transaction and matching
  database. Standalone catalog connections expose reads; writes fail closed.
  `commit_result(..., mutation=...)` serializes under BEGIN IMMEDIATE and commits
  domain rows, attempt result, logical terminal result and audit event together.
  An injected audit-insert failure rolls back the catalog row as well.
- Logical request identity excludes only attempt_id. Every attempt stores its
  exact context/request and its result. A known FAILED attempt may be archived
  with `terminal=False`, without domain mutations; a new attempt can then complete
  under the same key. Changed requests/attempt reuse are rejected. Exact replay
  returns the original event without running domain mutations again.
  OUTCOME_UNKNOWN stays terminal; no automatic redispatch is introduced.
- Capabilities are opaque process-local handles from a trusted LocalAuthority.
  No principals are allowed by default. Explicit grants bind an exact actor/session
  and registered event prefixes. Caller-supplied HUMAN labels, unknown events,
  forged handles and revoked grants fail. Human principals require a verified
  session configured by trusted application composition. This is not an OS sandbox,
  a login UI or official portal permission. Never expose capability issuance to models.
- Snapshot source receipts retain missing and failed dispositions. These are evidence;
  downstream coverage must qualify conclusions. Stored snapshots cannot be edited
  in place; a trusted review creates a child revision instead.
- Schema export/check explicitly uses UTF-8 and LF. Regenerated the five corrupt
  schemas from models. Repository attributes enforce stable text/binary handling
  without changing the user's global Git configuration.

## API and limits

Callers must pass capability= to the kernel. Construct a catalog with kernel= using
the same database path, and place writes inside the kernel's mutation callback.
The old direct-write examples were test conveniences, not accepted application APIs;
tests now route them through a trusted test dispatcher and actual transactions.

No API promises database migration from earlier unaccepted prototype layouts,
power-loss/fsync durability, automatic retries, trusted login establishment or
full evaluator isolation. Retry budgets and provider completion policy remain
higher-level responsibilities. A03 will build revision/CAS and review services on
this boundary; this repair alone does not implement profile approval or finish CP1.
